# Database Schema & ERD: Campus Equipment Booking API

This document details the relational data model for the Campus Equipment Booking API, based on the actual [`schema.sql`](schema.sql) applied to Cloudflare D1.

---

## 1. Entity Relationship Diagram (ERD)

```text
+-------------------------+             +-------------------------+
|        equipment        |             |        bookings         |
+-------------------------+             +-------------------------+
| * id          : TEXT PK | 1         * | * id          : TEXT PK |
|   name        : TEXT    |<------------| * equipmentId : TEXT FK |
|   location    : TEXT    |             |   borrowerName: TEXT    |
+-------------------------+             |   startAt     : TEXT    |
                                        |   endAt       : TEXT    |
                                        |   purpose     : TEXT    |
                                        |   createdAt   : TEXT    |
                                        +-------------------------+
```

### Relationship
* **`equipment` 1 ---- * `bookings`**
* Each equipment record can have zero, one, or many bookings.
* Each booking must reference exactly one valid equipment record via foreign key (`bookings.equipmentId` $\rightarrow$ `equipment.id`).

---

## 2. Table Definitions

### Table: `equipment`
Stores the catalog of shared campus resources available for reservation.

| Column | Data Type | Constraints | Description |
|---|---|---|---|
| `id` | `TEXT` | `PRIMARY KEY` | Deterministic unique equipment ID (e.g., `"eq-1"`) |
| `name` | `TEXT` | `NOT NULL` | Human-readable name of the equipment |
| `location` | `TEXT` | `NOT NULL` | Building or room where the equipment is kept |

---

### Table: `bookings`
Stores scheduled reservations made by students and faculty.

| Column | Data Type | Constraints | Description |
|---|---|---|---|
| `id` | `TEXT` | `PRIMARY KEY` | Unique booking identifier (UUID generated by server) |
| `equipmentId` | `TEXT` | `NOT NULL`, `FOREIGN KEY` | References `equipment(id)` |
| `borrowerName` | `TEXT` | `NOT NULL` | Full name of the borrower |
| `startAt` | `TEXT` | `NOT NULL` | ISO 8601 UTC timestamp of reservation start |
| `endAt` | `TEXT` | `NOT NULL` | ISO 8601 UTC timestamp of reservation end |
| `purpose` | `TEXT` | `NOT NULL` | Intended reason for borrowing |
| `createdAt` | `TEXT` | `NOT NULL` | ISO 8601 UTC timestamp when record was created |

---

## 3. Key Constraints & Data Integrity

1. **Referential Integrity:**  
   `bookings.equipmentId` enforces a strict foreign key reference to `equipment(id)`. Bookings cannot be created or updated with nonexistent equipment IDs.
2. **Date Storage Format:**  
   All timestamps (`startAt`, `endAt`, `createdAt`) are stored as standardized ISO 8601 UTC strings (`YYYY-MM-DDTHH:mm:ss.sssZ`). This guarantees correct chronological comparison in SQLite using `<` and `>`.
3. **Parameter Binding:**  
   All SQL statements interact with D1 via parameterized placeholders (`?`), preventing SQL injection vulnerabilities.

## 4. Deterministic Seed Data

The database is seeded with two deterministic equipment records defined in [`schema.sql`](schema.sql):

```sql
INSERT OR IGNORE INTO equipment (id, name, location) VALUES ('eq-1', 'Projector A', 'Building 1');
INSERT OR IGNORE INTO equipment (id, name, location) VALUES ('eq-2', 'Camera B', 'Building 2');
```

| ID | Name | Location |
|---|---|---|
| `eq-1` | Projector A | Building 1 |
| `eq-2` | Camera B | Building 2 |
